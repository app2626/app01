# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

f9 is a Google Apps Script (GAS) web app — a Mobile Pre-Order/POS/invoice system (`clasp` project, `rootDir: src`). It's one of several sibling GAS apps in this monorepo (`actss`, `actop`, `f8`, `Office`, `bnn`, `ipur`, etc.) but has no shared code with them — treat it as fully standalone. `scriptId` and `.clasp.json` live at the project root; all real source is under `src/`: `Code.js` (server), `Index.html` (SPA shell + all `<template>` markup), `JS.html` + `JS_*.html` (all client JS, one `window.app` object — `JS.html` is the core: shared helpers, login/routing/`api`/`init`; each page module lives in its own `JS_<Name>.html` and attaches itself as `window.app.<module> = {...}`; `JS_Boot.html` holds the global listeners + bootstrap and MUST stay the last include in `Index.html`), `CSS.html` (all styling), `appsscript.json` (manifest).

## Commands

There is no build step or bundler. Development is edit-the-file-directly, then run the local test harness before any push:

```bash
npm test              # GAS serve-hazard check + server (Code.js against an in-memory GAS mock) + client (real Index/CSS/JS in headless Chrome)
npm run check:gas     # only the GAS comment-stripper check (tools/check-gas-serve.js) - seconds
npm run check:served -- <exec url>   # AFTER a deploy: fetch the served page, compile every <script> (tools/check-served.js)
npm run test:server  # ~205 checks, no browser needed
npm run test:client  # ~207 checks; needs Chrome/Edge (set CHROME_PATH if not in a standard location); screenshots land in tests/out/
```

The harness lives in `tests/` (`gasmock.js` = in-memory SpreadsheetApp/CacheService/LockService/etc., `server.test.js`, `client.test.js`). When changing seeded data or product counts, update the expected counts in `client.test.js`. It is not a substitute for a real deployment check. Deploy flow:

```bash
# Push local changes to the Apps Script project (updates @HEAD / the editor's live code only)
clasp push

# Update an EXISTING deployment in place (keeps its public /exec URL working) — NEVER a bare `clasp deploy`,
# which creates a new deployment with a different URL
clasp deploy -i <deploymentId> -d "<description>"

# List deployments to find the right <deploymentId> / confirm which one is the live public URL
clasp deployments
```

**`clasp push` alone does not update anything end users see.** It only updates `@HEAD` (the Apps Script editor's live code, viewable only by someone with edit access to the script, via a separate auth flow). Any already-created deployment (a versioned snapshot pinned to a public `/exec` URL) is frozen until you `clasp deploy -i` it explicitly. Confirm with the user which deployment is "live" before assuming a push is visible to real users — a push followed by silence is a common source of "why isn't my change showing up" confusion.

There is no local dev server, but `npm test` (above) is the pre-push gate. For a quick syntax-only check of the two source files:

```bash
node --check src/Code.js
# the client JS is HTML (<script> blocks) split across JS.html + JS_*.html — check them all together:
node -e "const fs=require('fs'); const t=fs.readdirSync('src').filter(f=>/^JS(_.*)?\.html$/.test(f)).map(f=>fs.readFileSync('src/'+f,'utf8')).join(String.fromCharCode(10)); const js=[...t.matchAll(/<script>([\s\S]*?)<\/script>/g)].map(m=>m[1]).join(String.fromCharCode(10)); fs.writeFileSync(process.env.TEMP+'/extract.js', js);"
node --check "$TEMP/extract.js"
```

The harness cannot reproduce what GAS does when *serving* the page — see the serve-time comment stripper gotcha below, and verify UI changes on the live deployment (open it in a **fresh tab**; the browser caches the old iframe content, so a stale page after a deploy usually means a cached tab — hard-reload or add `?nocache=1`).

**Tailwind is precompiled** (no runtime CDN): after adding/changing any Tailwind class in `Index.html`/`JS*.html`, run `npm run build:css` (`tools/build-css.js` → `src/TailwindCSS.html`, config in `tailwind.config.js`). Class names assembled from strings at runtime must be added to the `safelist` there or they silently get no CSS. Commit the regenerated `TailwindCSS.html`.

**GAS serve-time comment stripper is not string-aware**: a `/*` inside any string in a `<script>` deletes the rest of the file (white screen), and a `//` (e.g. `https://…`) inside a *template literal* (backticks) truncates that line and leaks following markup into attributes. `node --check` and `npm test` both pass on such code. Avoid both sequences in strings in `JS.html`/`Index.html` scripts (single/double-quoted `'https://…'` has been fine in practice). That "fine in practice" depends on the stripper's quote tracking staying in step: a regex literal with an unbalanced quote (a character class holding both a double and a single quote) shifts it, and the next `//` inside an ordinary quoted string further down the same file is then cut as a comment — this took the whole app down on @87/@88 (`JS_Settings.html` failed to parse, `window.app.systemSettings` undefined, every route showed "เชื่อมต่อไม่สำเร็จ"). Write quotes inside regexes as `"` / `'`, and keep `//` out of message strings anyway. To see what GAS really serves: `npm run check:served -- <exec url>` (fetches the `goog.script.init` payload — `\xNN` escapes, so not plain JSON — and compiles each `<script>` block of `userHtml`). GAS re-reads the script when serving (it rewrites `\x22` as `"`), so its stripper cannot be emulated exactly: `tools/check-gas-serve.js` (first step of `npm test`, and of CI) instead fails on the three known patterns — `/*` outside a real comment, `//` in a template literal, a regex holding both quote characters (single-kind regexes like `/"/g`, and `\/\/` escapes, are served fine). It flags both past outages (@87 JS_Settings, the JS_Pos news regex). A new hazard pattern found on the live site belongs in its rules + self-test cases.

**CI** (`.github/workflows/f9-test.yml` at the monorepo root, runs on pushes/PRs touching `f9/**`): `check:gas`, `node --check` of server + client scripts, Tailwind rebuilt and unchanged (`build:css` is byte-reproducible — a diff means a forgotten rebuild), then server + client tests on Ubuntu with Chrome (`client.test.js` adds `--no-sandbox` only when `CI` is set). It never deploys.

## Architecture

**Server (`Code.js`)**: one dispatcher, `apiHandler(action, payload, userToken)`, called from the client via `google.script.run`. Every mutation runs under `LockService.getScriptLock()`. Auth is a custom HMAC-signed bearer token (`generateToken_`/`verifyToken_`, 30-day expiry, `timingSafeEqual_` comparison), salted-SHA-256 password hashing with legacy-hash/plaintext auto-migration, and per-role checks re-verified server-side inside `apiHandler` (never trust the client's role claim) — Sales sees only its own branch's data, Manager has restricted field access on Orders, Admin is unrestricted. Login rate-limiting is 5 fails/5min via `CacheService`.

**Public surface — every server function name ends with `_` except six**: in GAS any top-level function whose name does not end in `_` can be called from the page with `google.script.run.<name>()`, and this web app is `ANYONE_ANONYMOUS`, so that means by anyone, without a login and without going through `apiHandler`. Until 2026-11-17 `generateToken`/`getSecretKey` were reachable this way (anyone could mint an Admin token). The only functions allowed without the underscore are `doGet`, `include`, `apiHandler`, `getPublicConfig`, `setupDatabase` and `resetMemberPasswordFromProperties` (the last two carry their own gate). Name every new server function `something_` — a test in `tests/server.test.js` (`PUBLIC SURFACE`) fails otherwise. A `_` function cannot be picked in the Apps Script editor's Run menu either, so a one-off maintenance function needs its own gate (Script property flag, like the password reset) and must be deleted after use.

**Checkout write order** (`processCheckout_`, 2026-11-17): stock column → Orders rows → InventoryLog. If the Orders write throws, the stock column is put back to the values read just before it was changed (same lock) and the checkout answers with the error; an InventoryLog failure after the order is saved does NOT fail the checkout (an error would make staff book twice) — it leaves a `CHECKOUT_WARN` row in AuditLog, and a failed coupon usage count leaves `COUPON_USAGE_ERROR`. Keep this order when adding another write to checkout: anything that can fail after the Orders write must not turn a saved order into an error answer.

**Image uploads** (`UPLOAD_IMAGE` → `uploadImage_`): Admin only; the type must be in `UPLOAD_IMAGE_TYPES_` (jpeg/png/webp/gif — no svg), the first bytes of the file must match that type (`imageBytesMatch_`, checked before Drive is touched) and the file extension is taken from the type, not from the client's file name. `logAudit_` passes user/action/details through `sanitizeSheetText_`. `GET_ALL_DATA` does not write for non-Admin callers: the Products spec-column backfill runs only for Admin, under the script lock (skipped when the lock is busy).

**CDN scripts are pinned** (`Index.html`, 2026-11-17): Chart.js, chartjs-plugin-datalabels, SweetAlert2, html2canvas, jsPDF and the Font Awesome stylesheet load from an exact version + file URL with `integrity="sha384-…"` and `crossorigin="anonymous"` — a script from the CDN runs with full access to the login token and the remembered password, so a floating tag (`@11`, no version) is not allowed (a client test checks every `<script src>`). To upgrade one: pick the exact version, compute the hash from the file (`curl -sL <url> | openssl dgst -sha384 -binary | openssl base64 -A`), change URL and hash together, run `npm test`. Google Fonts cannot carry a hash (the CSS differs per browser).

**Showing messages that are not written in the code** (`window.app.alertError(title, msg[, icon])` in `JS.html`): the second positional argument of `Swal.fire(title, x, icon)` is HTML, and server error messages can contain sheet or user text (product names, SKUs, typed values). Anything like `res.message`, `e.message` or a value from data goes through `alertError` (sent as `text`), or through `esc()` when it is part of a larger HTML message. `Swal.fire('…', '…', 'icon')` stays fine for fixed strings.

**Passwords and tokens** (2026-11-17; `hashPassword_` / `checkPassword_` / `pbkdf2Hex_` / `passwordStamp_` in `Code.js`): the Members `Password` cell holds `v2$<rounds>$<salt>$<hash>` — PBKDF2-HMAC-SHA256 with a random per-user salt, hand-rolled over `Utilities.computeHmacSha256Signature` because GAS has no PBKDF2 (a test compares it with Node's `crypto.pbkdf2Sync`). The round count (`PW_V2_ROUNDS_`, 2000) is stored in the value, so it can be raised without breaking old hashes — every round is one `Utilities` call, so time a real login on the deployment before raising it. Older values (SHA-256 with the fixed salt, unsalted SHA-256, plain text) still verify and are rewritten as v2 on the next successful login; a stored value that looks like a hash is never compared as plain text. Always verify with `checkPassword_`, never by comparing hashes yourself (a fresh salt makes every hash different), and update `looksLikePasswordHash_` if the format changes — the member form and CSV import pass a value through untouched when it looks like a hash. New passwords need 8–100 characters (`PW_MIN_LENGTH_`: change password, member form, CSV import; existing shorter passwords still log in). The token payload carries `pv`, an HMAC of the user's stored password value: `apiHandler` and `setupDatabase` reject a token whose `pv` no longer matches (`tokenMatchesUser_`), so changing or resetting a password ends every older session of that user; `CHANGE_PASSWORD` returns a fresh `token` for the page that made the change. On the client, `window.app.checkSession_` (called from `api`) sends the user back to the login page with a message when the server answers with an invalid/expired-token error.

**`GET_TABLE` is an allowlist** (`GET_TABLE_ROLES_` in `Code.js`): only the sheets named there can be read, each by the roles listed (Admin-only: Members, Settings, AuditLog, OrderStatusLog, Coupons, UI_Banners, News, NewsCategories; Admin/Manager: Target; everyone: the storefront tables, Orders/InventoryLog (Sales: own branch) and Invoices (non-Admin/Manager: own documents)). Any other sheet in the spreadsheet — a hand-made backup copy, for example — is refused for every role, Admin included. **A new sheet the page reads through `GET_TABLE` must be added there.**

**Member directory sent to the page** (`memberDirectory_` / `membersForRole_`): `GET_ALL_DATA.members` and the dashboard's `members` carry only `Name`, `Username`, `Role`, `Branch Code` (what the dashboard staff select and the Target page use) — never Password, Accessible Menus or other columns — and a Sales user gets only the members of their own branch (filtered after the dashboard cache, like orders). The full list is `GET_TABLE Members`, Admin only.

**Public order tracking** (`PUBLIC_TRACK_ORDER` → `publicTrackOrderLookup_`, the only action besides `LOGIN` that needs no token): the caller must send the order number AND at least the last 4 digits of the phone saved on the order — without them the answer is `require_phone` before the sheet is even read (so it never says whether an order number exists); an order saved without a phone cannot be opened this way. "Not found" and "wrong phone" return the same message. Wrong answers are counted in `CacheService`: 5 per order number in 15 minutes locks that number (`TRACK_FAIL_<ID>`), 100 overall in 10 minutes closes public tracking for everyone (`TRACK_FAIL_ALL` — GAS gives no caller IP, so there is no per-caller limit). The result is masked (name, phone) and carries no `Remark`. Keep new fields out of it unless they are safe to show to someone who only guessed 4 digits.

**Sheets and how they're accessed — this distinction matters a lot when changing schema:**
- Most sheets (`Products`, `Branches`, `Channels`, `Promotions`, `Interests`, `GiftMappings`, `AutoPromotions`, `Members`) are read via `getTableDataAsJson_(sheet, skipCache)`, which maps the live header row to object keys dynamically (`headers.forEach((h,i) => obj[h] = row[i])`), and written via `saveRecord_()`, which does the same in reverse (`headers.map(h => dataObj[h])`). **These sheets are safe to reorder columns in** — nothing hardcodes a position. The one invariant that must hold: no two columns can share the same header text at the same time (the object-key collision silently drops one of them, both on read and on write).
- `Orders` is the opposite: `processCheckout_()` builds new rows as **positional arrays** (`orderRows.push([...])`, 3 separate call sites — main item row, gift row, discount row — all must stay the same length as `ORDERS_HEADERS_`), and there's a hard guard at the top of checkout that throws if the live sheet's header order doesn't exactly match `ORDERS_HEADERS_`. **Never reorder `Orders` columns in place.** To add a field to Orders, append it as a new trailing column (see the auto-retrofit pattern below) and extend `ORDERS_HEADERS_` to match — never insert in the middle.
- `UI_Banners` (hero/promo-grid/popup banner config) uses the same positional-array style as Orders (`data[i][1]`, `data[i][2]`, etc., not header-lookup) despite being edited generically. It has 10 columns (`Banner ID, Type, URL, Status, Target Link, Details, Title, Button Text, Start Date, End Date`); Start/End Date (cols 9-10, text `yyyy-MM-dd`, Thai time, blank = unbounded, End inclusive) schedule hero/grid/popup banners: `getAllInitialData_` (storefront) returns only `bannerScheduleState_ === 'live'` rows, `getSettingsList_` (admin) returns all with `startDate/endDate/schedule` so expired banners stay reusable. Write dates only via `writeBannerDates_` (forces text format — Sheets otherwise turns them into Date cells; `bannerDateStr_` normalises either on read). The filter runs at fetch time, so a page left open keeps showing a banner until its next data refresh.
- New trailing columns on `Orders`/`UI_Banners` are added via an idempotent retrofit run at the top of the relevant read path (`processCheckout_`'s `["Receipt No","Deposit",...].forEach(col => { if (missing) append })`, `ensureBannerColumns_()`) rather than a one-time migration script — this means older spreadsheets self-heal the first time they're touched after a deploy, with no manual migration step required. `getKeyValueSettings_(ss)`/`Settings` sheet is the generic key-value store (`SystemName`, `LogoUrl`, `DriveFolderId`, invoice company info, etc.) — also has this auto-append-if-missing behavior in `saveSettingsItem_`.
- `getTableDataAsJson_`'s cache (`CacheService`, 6h TTL, `TABLE_<name>` keys, only for the 7 tables listed above) is bypassed for Admin (`skipCache = secureUser.Role === 'Admin'`, passed from `GET_TABLE`/`GET_ALL_DATA`/`getAdvancedDashboard_`) so an Admin always sees live data — including edits made by hand directly in the Sheets UI, which don't trigger any of the app's own `cache.remove()` calls. Non-Admin roles still get the cached copy. Every write path also busts the relevant table's cache directly.

**Dashboard cache**: `GET_ADVANCED_DASHBOARD` serves a raw (pre-role-filter, Password-stripped) snapshot of Orders/Products/Members from `CacheService` (`DASH_BASE_*` chunks, 120s TTL; `dashCachePut_`/`dashCacheGet_`). `apiHandler` wraps `apiHandlerInner_` and invalidates it before and after every action NOT listed in `DASH_READ_ACTIONS_` — a new read-only action should be added there, a new write action needs nothing. The client's refresh button sends `{refresh:true}` to bypass it. Sales branch filtering and PII deobfuscation happen after the cache, never inside it.

**Settings backend rules** (`SETTING_RULES_` / `validateSettingValue_` / `validateBannerFields_` in `Code.js`): `SAVE_SETTINGS_ITEM` only accepts `type` in `bookingsettings` + `BANNER_TYPES_`, and `bookingsettings` only accepts keys listed in `SETTING_RULES_` (unknown key = whole save rejected, validation runs before any write; a value equal to what is already stored is not re-validated). **A new Settings key must be added to `SETTING_RULES_` or it cannot be saved.** Keys matching `SETTING_SECRET_KEY_RE_` (webhook/secret/token/password/apikey) plus `DriveFolderId` are stripped from `GET_ALL_DATA` (`publicSettings_`) and redacted in AuditLog; only `GET_SETTINGS_LIST` (Admin) returns them. Banner edits must send `bannerId` (UI_Banners is positional; the server verifies ID + type at the row before overwriting/deleting), and banner links must be http(s) or `#route`.

**Product deep links**: `?p=<Model>` (storefront `sharedModel` → `paramsFromState`/`applyUrlParams`). Share URLs are built from `window.__APP_URL` (`ScriptApp.getService().getUrl()` injected by `doGet`). `doGet` also injects `window.__DEEP_MODEL` (the sanitized `p`, `<>&`/control chars stripped, ≤120 chars — it lands inside a `<script>` via `JSON.stringify`, which does not escape `</script>`, so any new user-controlled value injected this way needs the same treatment); a link with `p` and no hash lands on `#pos` instead of `#dashboard`. Footer contact info comes from Settings keys `ContactPhone`/`ContactLine`/`ContactHours` (`renderFooterContact`).

**Products has its own multi-SKU add/edit flow** (`window.app.productGroup` in `JS_ProductGroup.html`, `saveProductGroup_`/`updateProductGroup_` in `Code.js`) that fully replaces the generic single-row grid form for this one table (`grid.handleAddClick()`/`grid.editForm()` both special-case `tableName === 'Products'` and divert here). One request can add several SKU variants (color/capacity/stock/per-SKU image override) sharing one Model's common fields (Marketing Model, Product Group, Price, etc.); submitting an existing Model appends new SKUs to it instead of creating a duplicate (detected server-side by exact Model-string match, never trusting a client flag). Editing operates by deleting all rows of a Model and rewriting the full set — the Model field itself is guarded against renaming server-side even though the client also disables it in the UI (disabled inputs still submit their value, so the server check is the real guard). `Product Name` is never typed directly; it's always derived (`buildAutoProductName_(model, color)`), both client- and server-side.

**Product categories**: `โมบาย`, `แท็บเล็ต`, `อุปกรณ์เสริม`, `สมาร์ทวอทช์`, `หูฟัง`, `ของแถมแบรนด์`, `ของแถมช่องทาง`. The list is repeated in `#pgCategory` (`Index.html`), the Products column options + `apKnownCats` (`JS.html`), the dashboard/analytics device lists (`JS_Dashboard.html`, `JS_Analytics.html` — report counting goes through `window.app.isMobileCat` = `โมบาย` + `แท็บเล็ต` together for the "โมบาย" KPI/charts/Target; `อุปกรณ์เสริม`/`สมาร์ทวอทช์`/`หูฟัง` form the "อุปกรณ์เสริม" bucket; the 1-per-order checkout limit still applies to `โมบาย` only) and `pos.storeCategories`; add a new category to all of them. The product form sets the select through `productGroup.setCategory` (adds an unknown stored category as a temporary option) and both client and server reject a blank Category — a missing option used to blank the select and wipe the category on save.

**Products CSV import** (`IMPORT_PRODUCTS` → `importProducts_` in `Code.js`; UI in `JS_ProductGroup.html` `openImport`/`handleImportFile`/`showImportPreview`, button `#gridImportBtn` shown only on Products): Admin-only, adds NEW SKUs only (existing/duplicate SKUs are skipped and reported, never overwritten), max 1000 rows. The client parses the CSV and calls with `dryRun:true` for the preview, then again with `dryRun:false`; the server re-validates every row each time (never trust the dry run). Product Name is always derived (`buildAutoProductName_`); a Model that already exists (sheet or earlier in the file) keeps its shared fields (price, capacity, ...) with a warning on mismatch; free-text cells go through `sanitizeSheetText_`, SKUs starting with `=+-@` are rejected. `BULK_UPDATE_PRODUCTS` accepts both the quick-edit modal's keys (`SKU/Price/Original Price/Stock Qty/Status`) and the API-style lowercase keys — keep both when touching it.

**Branches / Channels / Members / GiftMappings CSV import** (`IMPORT_RECORDS` → `importRecords_`, specs in `IMPORT_RECORD_TABLES_` in `Code.js`; UI in `JS_Import.html` `window.app.importer`; the shared `#gridImportBtn` routes through `grid.handleImportClick`): same contract as the product import (Admin-only, new rows only — duplicate IDs skipped, dryRun preview, server re-validates, max 1000 rows, ID/text columns written with `setNumberFormat('@')`, `8.65E+13`-style IDs rejected via `isSciNotation_`, Excel `="123"`/`'123` text forms unwrapped by `importCell_`). Table-specific: Branches need Channel (the storefront's channel list is the distinct `Branches.Channel` values, not the Channels sheet); Channels auto-number blank IDs as `CH-nn` after the highest existing (only for rows that pass validation); Members: Username dup check is case-insensitive, Role must be Admin/Manager/Sales, Branch Code must exist (or ALL), passwords are always hashed server-side, a blank password gets a random 16-char one returned in `generatedPasswords` ONLY on the real run and shown once in a non-dismissable dialog (never in AuditLog, `GET_ALL_DATA`, or the dryRun response). GiftMappings: blank Mapping ID auto-numbers `GM-nnn`; Target + at least one of Brand Gifts/Channel Gifts required; Status normalised to `เปิด`/`ปิด` (blank = เปิด); an unknown Channel token only warns. To make another table importable add an entry to `IMPORT_RECORD_TABLES_` (+ a branch in the row loop if it has rules) and an entry in `importer.TABLES` + the table list in `grid.init`'s button toggle.

**Content admin pages (Banners / News / News categories)** — Otis-CMS-style list pages from one module, `window.app.cms` in `JS_Cms.html` (menu ids `banners`, `news`, `newscats` under System Settings → Content; Admin only). Each kind is a config object in `cms.cfg()` (filters, columns, edit form, load/save/remove); list/filter/sort/paginate run client-side, all validation is server-side. Banners reuse the existing `GET_SETTINGS_LIST` / `SAVE_SETTINGS_ITEM` / `DELETE_SETTINGS_ITEM` (UI_Banners rules above still apply; `loginbg` stays in General Settings; no Seq/creator columns exist for banners). The old Hero/Promo Grid/Popup tabs and their card editor in `JS_Settings.html` were removed — the `banners` page is the only banner editor; hashes `#herobanners/#promogrids/#popupbanners` redirect to `#banners` and those ids in a member's Accessible Menus count as access to `banners`. News has its own sheets `News` (positional like Orders — append-only columns, `NEWS_HEADERS_`) and `NewsCategories`, auto-created by `ensureNewsSheets_` the first time an Admin opens the page (header mismatch throws, never overwrites); actions `NEWS_LIST/SAVE/DELETE/SET_SEQ/CAT_SAVE/CAT_DELETE`. Storefront gets `news` in `GET_ALL_DATA` via `getLiveNews_` (Active + in date window, no creator fields, no sheet creation) and the storefront renders it as a card row above the popular shelf (`pos.renderNewsShelf`, `#posNews`; click → `pos.openNews` Swal detail; hidden while searching/filtering/page 2+; Swal `title` is HTML so it goes through `esc()`). A category in use cannot be deleted; renaming cascades to its news. Table styling for all pages is the global `#page-content table` rule in `CSS.html` (Otis look, `!important` over per-page Tailwind). Never put `/*` in a string in these scripts (e.g. `accept="image/*"` white-screens GAS) — use explicit MIME lists.

**Target page add / edit / delete / CSV import** (`#target` → `window.app.target` in `JS_Target.html`; server `TARGET_SAVE` / `TARGET_DELETE` / `TARGET_IMPORT` → `saveTarget_` / `deleteTarget_` / `importTargets_` in `Code.js`, 2026-11-24): Admin only (Manager still sees the report, without `#targetAdminBar` and the `#targetActTh` column). A target row is identified by its name (Area / Branch Code / Branch Name / Username / `ALL BRANCHES`, case-insensitive, unique) and the server always finds the row by name — never a client row index; the name and target columns are found from the header the same way as `target.render` (`targetSheet_`, which also creates a missing `Target` sheet with `Area | เป้า`). Names starting with `=+-@` are refused, the target is a whole number ≥ 0 (commas allowed). The CSV import adds new names and UPDATES the target of existing ones (unlike the other imports, which only add), never deletes, max `TARGET_MAX_IMPORT_` (500) rows, preview via `dryRun` first and re-checked on the real run; `target.parseFile` skips the `รวมทั้งหมด` row. Row buttons call `openForm(idx)` / `remove(idx)` with an index into `target.rows` (no sheet text in `onclick`); after a save the page reloads first, then the toast shows.

**Bulk delete** (`DELETE_RECORDS` → `deleteRecords_`, `BULK_DELETE_TABLES_` in `Code.js`; client `grid.BULK_TABLES`/`toggleOne`/`toggleAll`/`deleteSelected`): Admin-only, whitelisted tables (Products, Branches, Channels, Members, GiftMappings, AutoPromotions, Promotions), the ID column comes from the server table (never from the client), max 200, first matching row per ID, a Member cannot delete their own account, cache busted + AuditLog `BULK_DELETE`. To enable another table add it to BOTH lists.

**Bulk status** (`BULK_SET_STATUS` → `bulkSetStatus_`, `BULK_STATUS_TABLES_` in `Code.js`; client `grid.STATUS_TABLES`/`setSelectedStatus`, buttons `#gridBulkOnBtn`/`#gridBulkOffBtn`): same selection + rules as bulk delete, only for tables that really have a `Status` column (Products, GiftMappings, AutoPromotions, Promotions); status must be an explicit เปิด/ปิด; only changed rows are written.

**Emergency password reset** (`resetMemberPasswordFromProperties` in `Code.js`): project owner sets Script properties `MPOS_RESET_ENABLE=true`, `MPOS_RESET_USERNAME`, `MPOS_RESET_PASSWORD` (≥8 chars) and runs the function from the Apps Script editor. **Login "remember"** (`#loginRemember`, `loadRememberedLogin` / `handleLogin` in `JS.html`): when the box is ticked a successful login stores `{u, p}` — username AND the plain password — in `localStorage['tg_pos_remember']` of that browser and the next visit fills both fields; logging in with the box unticked removes the entry. **Test harness notes**: `tests/gasmock.js` is a hand-written subset of the GAS API — add any new Sheet/Range method a server change needs (e.g. `getMaxRows`). **Dark mode** is a real per-viewer toggle (`html.dark` class), not a separate theme build — it works by overriding Tailwind *utility classes* wholesale in `CSS.html` (`html.dark .bg-indigo-50 { ... !important }`, `html.dark .text-black { ... !important }`, etc.), so any element built from those same utility classes gets dark-mode-correct colors automatically. The one thing this doesn't cover is CSS written as literal hex/ID-selector rules outside the Tailwind-class system (e.g. `#dataTable th`) — those need an explicit `html.dark #dataTable th { ... }` companion rule, easy to forget. The `indigo` and `slate` Tailwind color scales are remapped in `tailwind.config.js` (precompiled — see above; the old runtime-CDN `window.tailwind` assignment is gone). Tailwind's own `borderRadius`/`backdropBlur` overrides were intentionally left out. The remap (`indigo` → a navy/teal brand palette, not stock purple-indigo) — check `tailwind.config.js` before assuming a Tailwind color name maps to its default hex.
