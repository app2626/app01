# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

f9 is a Google Apps Script (GAS) web app — a Mobile Pre-Order/POS/invoice system (`clasp` project, `rootDir: src`). It's one of several sibling GAS apps in this monorepo (`actss`, `actop`, `f8`, `Office`, `bnn`, `ipur`, etc.) but has no shared code with them — treat it as fully standalone. `scriptId` and `.clasp.json` live at the project root; all real source is under `src/`: `Code.js` (server), `Index.html` (SPA shell + all `<template>` markup), `JS.html` + `JS_*.html` (all client JS, one `window.app` object — `JS.html` is the core: shared helpers, login/routing/`api`/`init`; each page module lives in its own `JS_<Name>.html` and attaches itself as `window.app.<module> = {...}`; `JS_Boot.html` holds the global listeners + bootstrap and MUST stay the last include in `Index.html`), `CSS.html` (all styling), `appsscript.json` (manifest).

## Commands

There is no build step or bundler. Development is edit-the-file-directly, then run the local test harness before any push:

```bash
npm test              # server (Code.js against an in-memory GAS mock) + client (real Index/CSS/JS in headless Chrome)
npm run test:server  # ~154 checks, no browser needed
npm run test:client  # ~150 checks; needs Chrome/Edge (set CHROME_PATH if not in a standard location); screenshots land in tests/out/
```

The harness lives in `tests/` (`gasmock.js` = in-memory SpreadsheetApp/CacheService/LockService/etc., `server.test.js`, `client.test.js`). When changing seeded data or product counts, update the expected counts in `client.test.js`. It is not a substitute for a real deployment check. Deploy flow:

```bash
# Push local changes to the Apps Script project (updates @HEAD / the editor's live code only)
clasp push

# Update an EXISTING deployment in place (keeps its public /exec URL working) — NEVER a bare `clasp deploy`,
# which creates a new deployment with a different URL
clasp deploy -i <deploymentId> -d "<description>"

# List deployments to find the right <deploymentId> / confirm which one is the live public URL
clasp deployments
```

**`clasp push` alone does not update anything end users see.** It only updates `@HEAD` (the Apps Script editor's live code, viewable only by someone with edit access to the script, via a separate auth flow). Any already-created deployment (a versioned snapshot pinned to a public `/exec` URL) is frozen until you `clasp deploy -i` it explicitly. Confirm with the user which deployment is "live" before assuming a push is visible to real users — a push followed by silence is a common source of "why isn't my change showing up" confusion.

There is no local dev server, but `npm test` (above) is the pre-push gate. For a quick syntax-only check of the two source files:

```bash
node --check src/Code.js
# the client JS is HTML (<script> blocks) split across JS.html + JS_*.html — check them all together:
node -e "const fs=require('fs'); const t=fs.readdirSync('src').filter(f=>/^JS(_.*)?\.html$/.test(f)).map(f=>fs.readFileSync('src/'+f,'utf8')).join(String.fromCharCode(10)); const js=[...t.matchAll(/<script>([\s\S]*?)<\/script>/g)].map(m=>m[1]).join(String.fromCharCode(10)); fs.writeFileSync(process.env.TEMP+'/extract.js', js);"
node --check "$TEMP/extract.js"
```

The harness cannot reproduce what GAS does when *serving* the page — see the serve-time comment stripper gotcha below, and verify UI changes on the live deployment (open it in a **fresh tab**; the browser caches the old iframe content, so a stale page after a deploy usually means a cached tab — hard-reload or add `?nocache=1`).

**Tailwind is precompiled** (no runtime CDN): after adding/changing any Tailwind class in `Index.html`/`JS*.html`, run `npm run build:css` (`tools/build-css.js` → `src/TailwindCSS.html`, config in `tailwind.config.js`). Class names assembled from strings at runtime must be added to the `safelist` there or they silently get no CSS. Commit the regenerated `TailwindCSS.html`.

**GAS serve-time comment stripper is not string-aware**: a `/*` inside any string in a `<script>` deletes the rest of the file (white screen), and a `//` (e.g. `https://…`) inside a *template literal* (backticks) truncates that line and leaks following markup into attributes. `node --check` and `npm test` both pass on such code. Avoid both sequences in strings in `JS.html`/`Index.html` scripts (single/double-quoted `'https://…'` has been fine in practice).

## Architecture

**Server (`Code.js`)**: one dispatcher, `apiHandler(action, payload, userToken)`, called from the client via `google.script.run`. Every mutation runs under `LockService.getScriptLock()`. Auth is a custom HMAC-signed bearer token (`generateToken`/`verifyToken`, 30-day expiry, `timingSafeEqual` comparison), salted-SHA-256 password hashing with legacy-hash/plaintext auto-migration, and per-role checks re-verified server-side inside `apiHandler` (never trust the client's role claim) — Sales sees only its own branch's data, Manager has restricted field access on Orders, Admin is unrestricted. Login rate-limiting is 5 fails/5min via `CacheService`.

**Sheets and how they're accessed — this distinction matters a lot when changing schema:**
- Most sheets (`Products`, `Branches`, `Channels`, `Promotions`, `Interests`, `GiftMappings`, `AutoPromotions`, `Members`) are read via `getTableDataAsJson(sheet, skipCache)`, which maps the live header row to object keys dynamically (`headers.forEach((h,i) => obj[h] = row[i])`), and written via `saveRecord()`, which does the same in reverse (`headers.map(h => dataObj[h])`). **These sheets are safe to reorder columns in** — nothing hardcodes a position. The one invariant that must hold: no two columns can share the same header text at the same time (the object-key collision silently drops one of them, both on read and on write).
- `Orders` is the opposite: `processCheckout()` builds new rows as **positional arrays** (`orderRows.push([...])`, 3 separate call sites — main item row, gift row, discount row — all must stay the same length as `ORDERS_HEADERS_`), and there's a hard guard at the top of checkout that throws if the live sheet's header order doesn't exactly match `ORDERS_HEADERS_`. **Never reorder `Orders` columns in place.** To add a field to Orders, append it as a new trailing column (see the auto-retrofit pattern below) and extend `ORDERS_HEADERS_` to match — never insert in the middle.
- `UI_Banners` (hero/promo-grid/popup banner config) uses the same positional-array style as Orders (`data[i][1]`, `data[i][2]`, etc., not header-lookup) despite being edited generically. It has 10 columns (`Banner ID, Type, URL, Status, Target Link, Details, Title, Button Text, Start Date, End Date`); Start/End Date (cols 9-10, text `yyyy-MM-dd`, Thai time, blank = unbounded, End inclusive) schedule hero/grid/popup banners: `getAllInitialData` (storefront) returns only `bannerScheduleState_ === 'live'` rows, `getSettingsList` (admin) returns all with `startDate/endDate/schedule` so expired banners stay reusable. Write dates only via `writeBannerDates_` (forces text format — Sheets otherwise turns them into Date cells; `bannerDateStr_` normalises either on read). The filter runs at fetch time, so a page left open keeps showing a banner until its next data refresh.
- New trailing columns on `Orders`/`UI_Banners` are added via an idempotent retrofit run at the top of the relevant read path (`processCheckout`'s `["Receipt No","Deposit",...].forEach(col => { if (missing) append })`, `ensureBannerColumns_()`) rather than a one-time migration script — this means older spreadsheets self-heal the first time they're touched after a deploy, with no manual migration step required. `getKeyValueSettings(ss)`/`Settings` sheet is the generic key-value store (`SystemName`, `LogoUrl`, `DriveFolderId`, invoice company info, etc.) — also has this auto-append-if-missing behavior in `saveSettingsItem`.
- `getTableDataAsJson`'s cache (`CacheService`, 6h TTL, `TABLE_<name>` keys, only for the 7 tables listed above) is bypassed for Admin (`skipCache = secureUser.Role === 'Admin'`, passed from `GET_TABLE`/`GET_ALL_DATA`/`getAdvancedDashboard`) so an Admin always sees live data — including edits made by hand directly in the Sheets UI, which don't trigger any of the app's own `cache.remove()` calls. Non-Admin roles still get the cached copy. Every write path also busts the relevant table's cache directly.

**Dashboard cache**: `GET_ADVANCED_DASHBOARD` serves a raw (pre-role-filter, Password-stripped) snapshot of Orders/Products/Members from `CacheService` (`DASH_BASE_*` chunks, 120s TTL; `dashCachePut_`/`dashCacheGet_`). `apiHandler` wraps `apiHandlerInner_` and invalidates it before and after every action NOT listed in `DASH_READ_ACTIONS_` — a new read-only action should be added there, a new write action needs nothing. The client's refresh button sends `{refresh:true}` to bypass it. Sales branch filtering and PII deobfuscation happen after the cache, never inside it.

**Settings backend rules** (`SETTING_RULES_` / `validateSettingValue_` / `validateBannerFields_` in `Code.js`): `SAVE_SETTINGS_ITEM` only accepts `type` in `bookingsettings` + `BANNER_TYPES_`, and `bookingsettings` only accepts keys listed in `SETTING_RULES_` (unknown key = whole save rejected, validation runs before any write; a value equal to what is already stored is not re-validated). **A new Settings key must be added to `SETTING_RULES_` or it cannot be saved.** Keys matching `SETTING_SECRET_KEY_RE_` (webhook/secret/token/password/apikey) plus `DriveFolderId` are stripped from `GET_ALL_DATA` (`publicSettings_`) and redacted in AuditLog; only `GET_SETTINGS_LIST` (Admin) returns them. Banner edits must send `bannerId` (UI_Banners is positional; the server verifies ID + type at the row before overwriting/deleting), and banner links must be http(s) or `#route`.

**Product deep links**: `?p=<Model>` (storefront `sharedModel` → `paramsFromState`/`applyUrlParams`). Share URLs are built from `window.__APP_URL` (`ScriptApp.getService().getUrl()` injected by `doGet`). `doGet` also injects `window.__DEEP_MODEL` (the sanitized `p`, `<>&`/control chars stripped, ≤120 chars — it lands inside a `<script>` via `JSON.stringify`, which does not escape `</script>`, so any new user-controlled value injected this way needs the same treatment); a link with `p` and no hash lands on `#pos` instead of `#dashboard`. Footer contact info comes from Settings keys `ContactPhone`/`ContactLine`/`ContactHours` (`renderFooterContact`).

**Products has its own multi-SKU add/edit flow** (`window.app.productGroup` in `JS_ProductGroup.html`, `saveProductGroup`/`updateProductGroup` in `Code.js`) that fully replaces the generic single-row grid form for this one table (`grid.handleAddClick()`/`grid.editForm()` both special-case `tableName === 'Products'` and divert here). One request can add several SKU variants (color/capacity/stock/per-SKU image override) sharing one Model's common fields (Marketing Model, Product Group, Price, etc.); submitting an existing Model appends new SKUs to it instead of creating a duplicate (detected server-side by exact Model-string match, never trusting a client flag). Editing operates by deleting all rows of a Model and rewriting the full set — the Model field itself is guarded against renaming server-side even though the client also disables it in the UI (disabled inputs still submit their value, so the server check is the real guard). `Product Name` is never typed directly; it's always derived (`buildAutoProductName_(model, color)`), both client- and server-side.

**Product categories**: `โมบาย`, `แท็บเล็ต`, `อุปกรณ์เสริม`, `สมาร์ทวอทช์`, `หูฟัง`, `ของแถมแบรนด์`, `ของแถมช่องทาง`. The list is repeated in `#pgCategory` (`Index.html`), the Products column options + `apKnownCats` (`JS.html`), the dashboard/analytics device lists (`JS_Dashboard.html`, `JS_Analytics.html` — report counting goes through `window.app.isMobileCat` = `โมบาย` + `แท็บเล็ต` together for the "โมบาย" KPI/charts/Target; `อุปกรณ์เสริม`/`สมาร์ทวอทช์`/`หูฟัง` form the "อุปกรณ์เสริม" bucket; the 1-per-order checkout limit still applies to `โมบาย` only) and `pos.storeCategories`; add a new category to all of them. The product form sets the select through `productGroup.setCategory` (adds an unknown stored category as a temporary option) and both client and server reject a blank Category — a missing option used to blank the select and wipe the category on save.

**Products CSV import** (`IMPORT_PRODUCTS` → `importProducts` in `Code.js`; UI in `JS_ProductGroup.html` `openImport`/`handleImportFile`/`showImportPreview`, button `#gridImportBtn` shown only on Products): Admin-only, adds NEW SKUs only (existing/duplicate SKUs are skipped and reported, never overwritten), max 1000 rows. The client parses the CSV and calls with `dryRun:true` for the preview, then again with `dryRun:false`; the server re-validates every row each time (never trust the dry run). Product Name is always derived (`buildAutoProductName_`); a Model that already exists (sheet or earlier in the file) keeps its shared fields (price, capacity, ...) with a warning on mismatch; free-text cells go through `sanitizeSheetText_`, SKUs starting with `=+-@` are rejected. `BULK_UPDATE_PRODUCTS` accepts both the quick-edit modal's keys (`SKU/Price/Original Price/Stock Qty/Status`) and the API-style lowercase keys — keep both when touching it.

**Branches / Channels / Members / GiftMappings CSV import** (`IMPORT_RECORDS` → `importRecords`, specs in `IMPORT_RECORD_TABLES_` in `Code.js`; UI in `JS_Import.html` `window.app.importer`; the shared `#gridImportBtn` routes through `grid.handleImportClick`): same contract as the product import (Admin-only, new rows only — duplicate IDs skipped, dryRun preview, server re-validates, max 1000 rows, ID/text columns written with `setNumberFormat('@')`, `8.65E+13`-style IDs rejected via `isSciNotation_`, Excel `="123"`/`'123` text forms unwrapped by `importCell_`). Table-specific: Branches need Channel (the storefront's channel list is the distinct `Branches.Channel` values, not the Channels sheet); Channels auto-number blank IDs as `CH-nn` after the highest existing (only for rows that pass validation); Members: Username dup check is case-insensitive, Role must be Admin/Manager/Sales, Branch Code must exist (or ALL), passwords are always hashed server-side, a blank password gets a random 16-char one returned in `generatedPasswords` ONLY on the real run and shown once in a non-dismissable dialog (never in AuditLog, `GET_ALL_DATA`, or the dryRun response). GiftMappings: blank Mapping ID auto-numbers `GM-nnn`; Target + at least one of Brand Gifts/Channel Gifts required; Status normalised to `เปิด`/`ปิด` (blank = เปิด); an unknown Channel token only warns. To make another table importable add an entry to `IMPORT_RECORD_TABLES_` (+ a branch in the row loop if it has rules) and an entry in `importer.TABLES` + the table list in `grid.init`'s button toggle.

**Content admin pages (Banners / News / News categories)** — Otis-CMS-style list pages from one module, `window.app.cms` in `JS_Cms.html` (menu ids `banners`, `news`, `newscats` under System Settings → Content; Admin only). Each kind is a config object in `cms.cfg()` (filters, columns, edit form, load/save/remove); list/filter/sort/paginate run client-side, all validation is server-side. Banners reuse the existing `GET_SETTINGS_LIST` / `SAVE_SETTINGS_ITEM` / `DELETE_SETTINGS_ITEM` (UI_Banners rules above still apply; `loginbg` stays in General Settings; no Seq/creator columns exist for banners). The old Hero/Promo Grid/Popup tabs and their card editor in `JS_Settings.html` were removed — the `banners` page is the only banner editor; hashes `#herobanners/#promogrids/#popupbanners` redirect to `#banners` and those ids in a member's Accessible Menus count as access to `banners`. News has its own sheets `News` (positional like Orders — append-only columns, `NEWS_HEADERS_`) and `NewsCategories`, auto-created by `ensureNewsSheets_` the first time an Admin opens the page (header mismatch throws, never overwrites); actions `NEWS_LIST/SAVE/DELETE/SET_SEQ/CAT_SAVE/CAT_DELETE`. Storefront gets `news` in `GET_ALL_DATA` via `getLiveNews_` (Active + in date window, no creator fields, no sheet creation) and the storefront renders it as a card row above the popular shelf (`pos.renderNewsShelf`, `#posNews`; click → `pos.openNews` Swal detail; hidden while searching/filtering/page 2+; Swal `title` is HTML so it goes through `esc()`). A category in use cannot be deleted; renaming cascades to its news. Table styling for all pages is the global `#page-content table` rule in `CSS.html` (Otis look, `!important` over per-page Tailwind). Never put `/*` in a string in these scripts (e.g. `accept="image/*"` white-screens GAS) — use explicit MIME lists.

**Bulk delete** (`DELETE_RECORDS` → `deleteRecords`, `BULK_DELETE_TABLES_` in `Code.js`; client `grid.BULK_TABLES`/`toggleOne`/`toggleAll`/`deleteSelected`): Admin-only, whitelisted tables (Products, Branches, Channels, Members, GiftMappings, AutoPromotions, Promotions), the ID column comes from the server table (never from the client), max 200, first matching row per ID, a Member cannot delete their own account, cache busted + AuditLog `BULK_DELETE`. To enable another table add it to BOTH lists.

**Bulk status** (`BULK_SET_STATUS` → `bulkSetStatus`, `BULK_STATUS_TABLES_` in `Code.js`; client `grid.STATUS_TABLES`/`setSelectedStatus`, buttons `#gridBulkOnBtn`/`#gridBulkOffBtn`): same selection + rules as bulk delete, only for tables that really have a `Status` column (Products, GiftMappings, AutoPromotions, Promotions); status must be an explicit เปิด/ปิด; only changed rows are written.

**Emergency password reset** (`resetMemberPasswordFromProperties` in `Code.js`): project owner sets Script properties `MPOS_RESET_ENABLE=true`, `MPOS_RESET_USERNAME`, `MPOS_RESET_PASSWORD` (≥8 chars) and runs the function from the Apps Script editor. It refuses without the enable flag (it is technically callable from the page, so the flag is the gate), writes a salted hash, clears the user's login rate-limit key, audits `RESET_PASSWORD` as `SCRIPT_OWNER`, never returns the password, and deletes all three properties on every run (success or failure).

**Status wording `เปิด`/`ปิด`**: NewsCategories, AutoPromotions, News and UI_Banners store `เปิด`/`ปิด` (helpers `statusOn_`/`statusOff_`/`statusFromInput_`/`migrateStatusColumn_` in `Code.js`, client `window.app.statusOn`). Old `Active`/`Inactive` values still read correctly and are migrated in place the first time an Admin opens the page (GET_TABLE for AutoPromotions, `ensureNewsSheets_`, `getSettingsList`). Never compare a status against the literal `'Active'`.

**Grid look** (`#tmpl-datagrid` in `Index.html`, `JS_Grid.html`): the generic table uses the banner page's `.cms-*` classes (title+crumb from `grid.TITLES`, `.cms-card`, `.cms-actions`, `.cms-bar` with `#gridPageSize`/`#gridSearch`, `.cms-ico` row buttons, `.cms-pager` in `#gridPagination`). Keep the element ids (`gridAddBtn`, `gridImportBtn`, `gridExportBtn`, `gridBulkQuickBtn`, `gridBulkDeleteBtn`, `gridFilterBar`, `gridSearch`, ...) — `grid.init` toggles them and tests use them. Toolbar order: add → bulk actions (delete/เปิด/ปิด, `disabled` until a row is selected — `syncSelection` toggles it) → `.cms-grow` spacer → tools (quick edit/import/export) right-aligned. Empty/error rows go through `grid.stateRow` (sticky `.cms-empty-pin` sized to the visible `.cms-wrap` via ResizeObserver) — a plain centred `colspan` cell lands off-screen in wide tables like Orders. Column `label`s in the `grid.init(...)` calls (`route()` in `JS.html`) are display-only Thai text (header + form); CSV export, save and sort use `key`, so labels can be renamed freely. Form title = `เพิ่ม`/`แก้ไข` + `grid.TITLES[table]` minus `จัดการ`.

**In-app `#page` links**: `Index.html` has `<base target="_top">` (needed inside the GAS iframe), so a native `<a href="#orders">` click does nothing on the live site while working fine in the local harness. The document click handler in `init` (`JS.html`) intercepts every `a[href^="#"]` whose href is `#<id>` and sets `location.hash` itself (a bare `#` and already-prevented clicks are left alone) — never rely on native hash navigation, and keep new page links as plain `#id` hrefs so the handler catches them.

**Reload keeps the current page** (`saveRoute_`/`savedRoute_`/`clearSavedRoute_` in `JS.html`): a pull-to-refresh reloads the GAS iframe and its `#hash` is lost, so `route()` stores the page id in `sessionStorage['f9_last_route']` (after the permission check) and the init code restores it when there is no hash (a shared `?p=` link still wins; logout clears it; the restored id goes through the normal access check again). Not restored: filters/search text, scroll position, open dialogs, unsaved form input.

**Popup banner carousel** (`showPopupBanner`/`popupGo`/`popupSlide` in `JS.html`, `.popup-*` in `CSS.html`, markup in `Index.html`): several popups = one `.popup-slide` each in a `translateX` track like the hero banner (5s auto-advance, pause on hover/touch, swipe, dots; single popup hides the controls).

**Generic CRUD (`grid` module in `JS_Grid.html`)** backs every other table's admin UI (a shared `<template id="tmpl-datagrid">`). It resolves which row to update in `saveRecord()` via a client-supplied `_rowIndex` (from the row object `getTableDataAsJson` already attached) when editing, or — for genuinely new records — checks the submitted ID against every existing row and rejects on collision (both client-side, for fast feedback, and server-side, as the actual enforcement; the client check alone is bypassable via a direct API call). ID fields with a client-side auto-generator (Promo ID, Channel ID, Mapping ID, Rule ID) are locked `disabled` on create as well as edit, so this collision path is mostly relevant to the three tables without one: Branches, Members, Interests.

**Frontend (`JS.html` core + `JS_*.html` modules)** is a single `window.app` object (core file first, modules attach to it, Boot last — add a new module file to the `include()` list in `Index.html`, the `tests/*.js` loaders pick up `include('JS*')` automatically, and `tailwind.config.js` already globs `JS_*.html`), no framework, no build step — plain template-literal HTML strings assigned to `.innerHTML`. Every string interpolated from user/sheet data goes through `window.app.esc()` (HTML-escape) or `escAttrJs()` (attribute-context escape) — this is the only XSS defense and it's manual per call site, not automatic. Images go through `formatImageUrl()`, which rewrites Google Drive share links into direct thumbnail URLs; uploads go through `selectImageForUpload()` (stages a local file in `pendingImageUploads[stateKey]`, previews immediately) then `flushImageUpload(stateKey)` (actually uploads to Drive) only at save time, not on file selection — this two-phase pattern is used everywhere images are editable (products, banners, invoice logos, login background, web app logo). Routing is a `menuConfig`-driven sidebar plus a `case` switch on a page identifier — there's no client-side router library.

**Server-side text sanitization** (`sanitizeSheetText_()`, a leading-`=+-@` formula-injection guard) is opt-in per column, via a `*_FREE_TEXT_COLS_`-style allowlist next to each write path (`SAVE_RECORD_FREE_TEXT_COLS_`, `PRODUCT_GROUP_FREE_TEXT_FIELDS_`, the `FREE_TEXT_COLS_` inside `updateFullOrder`) — **numeric/select/ID columns are deliberately excluded** (sanitizing a numeric column would corrupt it), so when adding a new free-text field to an existing table, it must be added to that table's allowlist explicitly or it silently ships unsanitized. This has happened before (`saveInvoice`'s `Invoice Date` field) — grep for `sanitizeSheetText_` near a save function before assuming a new field is covered.

**Storefront (`window.app.pos`)** keeps its filter state in `storeFilters` and mirrors it to the URL through `syncUrl`/`applyUrlParams` (`google.script.history`, because the app runs inside the GAS iframe and `window.location.search` never sees the outer URL). Public order tracking works the same way: `doGet` validates `?track=`/`?orderId=` (`^[A-Za-z0-9_-]{1,64}$`) and injects it as `window.__TRACK_PARAM` in `Index.html`. Product channel matching goes through `window.app.channelOk()` (`ALL`/`*`/`ทั้งหมด` = every channel) — but the storefront filter deliberately keeps the old strict match for gift rows, because `setupDatabase` seeds gifts with channel `ALL` and they must not become sellable cards. Sidebar option lists (Capacity/Color, like Series) are scoped to the selected Category and Series via `pos.optionScope_`; `pos.pruneOptionFilters_` drops selected capacities/colors that fall out of scope when the category/series changes (a hidden active filter would silently empty the grid). Cards group SKUs by `Model`, so price sorting uses each model's minimum price. Companion ("ซื้อคู่") suggestions are derived from `AutoPromotions` rules (`recommendCompanions`), with no extra sheet column; `window.app.NO_IMG` is the inline SVG placeholder used instead of external placeholder services.

**Storefront website mode** (`html.sf-site`, toggled in `route()` — on for `#pos` only, removed in `renderLogin`): the storefront looks like a normal shop website — CSS hides the admin `#desktopSidebar`/mobile app topbar/background blobs, centres `#page-content` (max 1320px) and strips the `.pos-shell-card` chrome. The pos template carries its own `#sfTopbar` (service links + `ContactPhone`) and a sticky `#posStoreHeader` (brand `.sf-home` → `pos.goHome`, search, wishlist `#posWishlistCountBadge`, cart, account menu `#sfAcctBtn`/`#sfAcctPop` built by `window.app.renderSiteHeader` from `menuConfig` + `checkMenuAccess` = the way into the back office). Full-width backgrounds use `::before` with ±100vmax (not clip-path — that clips the account dropdown). The old "เต็มจอ" button (`#posFullscreenBtn`) is gone; `toggleSidebar`/`f9_sidebar_hidden` still work on admin pages. Countdowns over 99 days show the closing date instead of a day counter. Desktop (≥1024px) shows a text category menu `#sfCatNav` (`pos.renderCatNav`, re-rendered by `renderStoreHeader`) and hides the category tiles (mobile keeps tiles); category order lives in one place, `pos.storeCategories()`. The footer (shared by all pages, 4 columns) has category links `#footerCatLinks` (`window.app.renderFooterCategories`, `window.app.goCategory` — sets `pos.storeFilters` then routes to `#pos` if needed) and turns dark navy in website mode. Don't reuse the class `.sf-brand` outside product cards (it is the card's brand line). Storefront dialogs/drawers (add-to-cart, checkout, compare, trade-in, quote, order track, cart, wishlist) use a white `.sf-dlg-head` header (no FLASH/TRADE-IN badges) and `.sf-btn-2` outline secondary buttons; one orange primary per footer. Floating bars (compare dock `#posCompareBar`, mobile cart `#posMobileStickyCart`, `#backToTopBtn`) are white too. **AutoPromotions `Message Suggest`/`Message Apply` are inserted as HTML — always through `window.app.safeRichText`** (escapes everything, re-allows only `b/strong/em/i/u/br` with a `[A-Za-z0-9 _:-]` class); use it for any other sheet text that needs light formatting. Back office: the full store footer (`.pf-grid`) shows only in website mode — admin pages keep just the copyright row; sidebar menu children are `flex-shrink: 0` (otherwise `truncate` section headers get squeezed to nothing in the scrolling flex column); the dashboard shows no banners or campaign grid at all (hero/promo-grid banners belong to the storefront only; `window.app.dashboard.slider`/`renderBanners` were removed). **Test harness notes**: `tests/gasmock.js` is a hand-written subset of the GAS API — add any new Sheet/Range method a server change needs (e.g. `getMaxRows`). **Dark mode** is a real per-viewer toggle (`html.dark` class), not a separate theme build — it works by overriding Tailwind *utility classes* wholesale in `CSS.html` (`html.dark .bg-indigo-50 { ... !important }`, `html.dark .text-black { ... !important }`, etc.), so any element built from those same utility classes gets dark-mode-correct colors automatically. The one thing this doesn't cover is CSS written as literal hex/ID-selector rules outside the Tailwind-class system (e.g. `#dataTable th`) — those need an explicit `html.dark #dataTable th { ... }` companion rule, easy to forget. The `indigo` and `slate` Tailwind color scales are remapped in `tailwind.config.js` (precompiled — see above; the old runtime-CDN `window.tailwind` assignment is gone). Tailwind's own `borderRadius`/`backdropBlur` overrides were intentionally left out. The remap (`indigo` → a navy/teal brand palette, not stock purple-indigo) — check `tailwind.config.js` before assuming a Tailwind color name maps to its default hex.
